虚拟环境与依赖管理

「昨天还能跑，今天升级一个包就崩了」几乎每个项目都遇到过一次。问题不在代码，而在依赖装在了公共抽屉里：谁都能改，谁都说不清版本。

认知路线 真实问题→ 直觉类比→ 形式化定义→ 结构与机制→ 案例→ 练习

学习目标

  1. 能创建、激活虚拟环境，并解释它隔离了什么、没隔离什么。
  2. 能用 requirements.txt 锁定版本并在另一台机器复现。
  3. 能判断什么时候必须建环境、什么时候可以省。

01一次升级，三个项目受影响

一台开发机上同时有三个项目，都直接装在系统 Python 里：

项目 A

教学示例

依赖 NumPy 2.5，代码里用了新的类型提升规则，运行正常。

项目 B

旧报表脚本

依赖旧版接口，升级后数组运算结果类型变了，报表数字对不上。

项目 C

临时试验

随手 pip install 了三个包，把公共环境又改了一遍。

三个项目都没有改代码，为什么 B 会突然坏掉？

因为依赖是共享的：任何一次安装或升级，都会同时改变所有项目看到的包版本。

02一个项目，一个工具箱

装修时不会把所有工具倒进一个抽屉：水电、木工、油漆各用各的箱子，缺什么补什么，完工后照单清点。

直觉结论

虚拟环境不是「另一台机器」，只是另一套解释器与包目录；它让版本可记录、可回滚、可复现。

03环境、清单与锁定

概念是什么解决什么
虚拟环境项目目录下的一套独立解释器与 site-packages项目之间互不踩踏
依赖清单requirements.txt 记录包名与版本约束换机可复现
版本锁定把版本写成 == 精确值，而非「最新版」避免自动升级引入变化

隔离的边界要说清：虚拟环境隔离的是 Python 解释器与第三方包，不隔离系统库、显卡驱动与环境变量；数据文件、模型权重也不在其中。所以「我建了 venv」不等于「结果一定可复现」，还要锁定版本、固定随机种子、记录数据版本。

常见误解

pip freeze 导出的是「当前装了什么」，不是「项目真正需要什么」。它会把传递依赖一起写进来，适合复现，不适合当人类可读的依赖声明。

04四条命令走完一轮

Windows 下从零到可复现，只需要下面四步（python 指 3.13 解释器）：

shellPowerShell / CMD
python -m venv .venv
.venv\Scripts\activate
python -m pip install "numpy==2.5.4" "matplotlib==3.11.2"
python -m pip freeze > requirements.txt

换一台机器时，不复制 .venv 目录（它含绝对路径，跨机器不可靠），而是重建并安装清单：

shell复现步骤
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt

版本以知识库口径为准：NumPy 2.5 系列、Matplotlib 3.11.2。安装后用一条命令核对，不需要凭记忆：

shell版本核对
python -c "import numpy, matplotlib; print(numpy.__version__, matplotlib.__version__)"

激活失败的常见原因是执行策略或路径：PowerShell 下可改用 .venv\Scripts\Activate.ps1，或直接在命令前写 .venv\Scripts\python.exe，不激活也能运行。

05两个项目的依赖冲突

把 A、B 两个项目放进各自的 .venv 后，冲突消失，但清单必须分开维护：

项目需要 NumPy共享环境下的结果独立环境下的结果
A 教学示例2.5.4被 B 的旧版本覆盖后无法运行按清单安装，稳定
B 旧报表旧接口版本被 A 升级后数字变化维持原版本，输出不变

项目 A 的清单可以写成这样，一眼能看出直接依赖：

textrequirements.txt（节选）
numpy==2.5.4
matplotlib==3.11.2

注意清单里没有 pip、setuptools 这类构建工具；pip freeze 会把它们一并导出，交付前建议手工删掉，或改用 pip-tools 只保留直接依赖。

06建环境、装三个包、换目录复现

任务：新建一个目录，完成下面四件事，并把每一步的命令与输出记进实验记录。

建环境在该目录执行 python -m venv .venv，确认目录里出现 pyvenv.cfg。
装三个包安装 numpy==2.5.4、matplotlib==3.11.2 与任意一个纯 Python 包，记录安装耗时与来源。
导出清单pip freeze > requirements.txt，打开文件，标出哪些是直接依赖、哪些是传递依赖。
换目录复现复制清单到新目录，重建环境并安装，用版本核对命令确认两个版本一致。

追问：① 为什么不能直接复制 .venv 到另一台机器？② 如果只写 numpy>=2.5，半年后复现可能遇到什么？

验收：新目录里 python -c "import numpy; print(numpy.__version__)" 输出 2.5.4，且清单中每个包都能说出「谁引入的」。

注：本页代码与「实测输出」的运行口径为 Python 3.13.14（Windows），结果来自本机实际运行，可直接复现。
