结构化查询语言：SPARQL、Cypher 与 SQL

同一个两跳问题，三种语言写出三种样子。它们不是三种能力，而是三种数据模型的外壳。

认知路线 真实问题→ 直觉类比→ 形式化定义→ 结构与机制→ 案例→ 练习

学习目标

  1. 能写出同一个两跳问题在 SPARQL、Cypher、SQL 中的基本形式。
  2. 能说出三种语言各自对应的数据模型与连接方式。
  3. 能判断一个查询场景更适合哪种语言，并说清理由。

01一个问题三种写法

问题很具体：星海科技收购的公司中，哪些位于北京。同一批事实，三个团队各存了一份。

数据平台把它放进关系表：公司表、收购表，城市是公司表的一个字段，DBA 用两次 JOIN 就能回答。图团队把它存成属性图：节点是公司，边是收购与位于，工程师画一条两段箭头。开放数据组用 RDF 发布：每条事实一个三元组，查询时写两组三元组模式，变量重名即连接。

三个人说的结论相同，写下的语句完全不同。差别不在谁更强，而在底下的模型长什么样。

02三种语言对照

把三种语言放在一张表里看，对应关系立刻清楚：语言是壳，模型是核。

图里三个「要点」栏是三种语言各自的抓手：SPARQL 靠变量绑定与 FILTER，Cypher 靠模式即路径、箭头定方向，SQL 靠主外键连接。学会一个，另外两个只需要换语法。

先选模型再选语言

事实以三元组发布、要跨库合并，用 SPARQL；事实是带属性的节点与边、要频繁遍历，用 Cypher；事实本来就在业务表里、要给报表用，用 SQL。

03写法定式

三种语言的核心写法，可以并排记住。

语言数据模型两跳怎么写关键机制
SPARQLRDF 三元组两组三元组模式，变量同名变量绑定 + FILTER
Cypher属性图一条路径，两段箭头模式匹配，方向写在箭头上
SQL关系表两次 JOIN，主外键对齐连接条件 + WHERE 过滤

三者都要交代四件事：起点是谁、走哪类边、朝哪个方向、附加什么过滤条件。区别只是表达方式——SPARQL 用重复变量表示「同一个节点」，Cypher 用箭头，SQL 用连接条件。

04两跳怎么落笔

三段的骨架如下，省略了前缀与建表语句。

sparqltwo_hop.rq
PREFIX ex: <http://example.org/>
SELECT ?c WHERE {
  ?a ex:收购 ?b .
  ?b ex:位于 ?c .
  FILTER(?a = ex:星海科技)
}
cyphertwo_hop.cypher
MATCH (a:公司 {名称: "星海科技"})-[:收购]->(b)-[:位于]->(c)
RETURN c.名称
sqltwo_hop.sql
SELECT b.名称
FROM 公司 a
JOIN 收购 ac ON a.id = ac.收购方
JOIN 公司 b ON b.id = ac.被收购方
WHERE a.名称 = '星海科技' AND b.城市 = '北京';

跳数上去，改动量不一样：SPARQL 多加一组三元组，Cypher 多接一段箭头，SQL 多一次 JOIN。两跳两次连接，三跳三次，连接数随跳数线性增长——这是 SQL 写长链查询时最容易失控的地方。

方向也要盯住。SPARQL 把 ?a 与 ?b 的位置对调就是反向；Cypher 把箭头反过来；SQL 换 ON 的连接列。写反了不会报错，只会安静地返回空集。

05各管一段

不说优劣，只说各自顺手的地方。

语言顺手的场景容易踩的坑
SPARQL开放数据端点、跨库合并、URI 全局标识前缀漏写；公共端点有配额
Cypher路径遍历、邻居扩展、工程侧图服务箭头写反；无索引的全图扫描
SQL报表、BI、事务系统、生态成熟漏 ON 条件产生笛卡尔积

一次真实的选型往往不是三选一：明细存在业务表里（SQL），关系层同步到图库供路径查询（Cypher），对外发布再接一个 RDF 端点（SPARQL）。三套并存，各答各的问题。

语言不产生语义能力

换个查询语言不会让系统更聪明。语义能力来自数据模型、实体标识与索引；语言只是把已有结构问出来。漏写 JOIN 条件的笛卡尔积，在三种语言里都救不回来。

06改写三遍

任务：把「星海科技收购的公司中，哪些公司的投资方位于北京」写成三种语言，并标出连接次数。

语言要写几段连接靠什么
SPARQL？组三元组变量同名
Cypher？段箭头路径连续
SQL？次 JOIN主外键条件

追问：① 这题是几跳？② 若「投资方」与「被投资方」方向写反，三种查询各自返回什么？③ 为什么公共 SPARQL 端点不建议做全库扫描？

验收：三种写法都能指出起点、边类型、方向与过滤条件。属性图与 RDF 的差别，见 属性图；三元组怎么组织，见 RDF。
