开放知识图谱：Wikidata、DBpedia、YAGO

冷启动阶段，先借一张公共骨架把系统跑起来，再补行业深度。

认知路线 真实问题→ 直觉类比→ 形式化定义→ 结构与机制→ 案例→ 练习

学习目标

  1. 能说出 Wikidata、DBpedia、YAGO 三者各自的来源与类型体系。
  2. 能解释开放图谱为什么能回答「CEO 是谁」，却答不了「上游供应商是谁」。
  3. 能读一段模式匹配代码的输出，判断缺失关系属于哪类知识。

01零数据的第一个问题

新项目刚立项，内部一条图谱数据都没有。业务方先问了两个最基础的问题：星海科技的 CEO 是谁？云计算行业里有哪些公司？

这两个问题不需要行业深度，只需要一张覆盖广的公共骨架：公司、人物、城市、行业，以及它们之间的基本关系。等骨架跑通、接口联调完成，再往里补供应商、产能、毛利率这些只有内部才有的关系。

开放知识图谱就是为这个阶段准备的。它不是行业数据库，别指望它替你回答业务问题。

02两种建法

同样是三元组，开放图谱和行业自建图谱的取舍正好相反：一个要广，一个要专；一个模式宽松，一个先定约束。

直觉结论

开放图谱负责「让人认识这家公司」，行业图谱负责「判断这家公司靠不靠谱」。

03三家开放图谱

图谱数据从哪来类型体系规模（量级随版本变化）
Wikidata社区众包编辑，人工加机器辅助自有属性体系，宽松、可随时扩千万级条目，多语言标签
DBpedia从维基百科信息框与分类自动抽取映射到公开本体，结构较规整百万级实体
YAGO融合维基百科与 WordNet借用 WordNet 的类层次，类型严谨百万级实体

三者的共同点是都用全局 URI 标识实体，因此可以互相指向、互相补全；差异在来源与类型严格程度：要覆盖广选 Wikidata，要结构规整选 DBpedia，要做类型推断选 YAGO。

易错点

把开放图谱当成免费行业数据库。它收录的是公共骨架，供应链、产能、客户合同这类关系不在其中，问它只会得到 0 条。

04模式匹配取子图

开放图谱对外主要提供两种用法：下载子图，或调用 SPARQL 端点。查询的本质是模式匹配——给出带变量的三元组，让引擎找出所有能填满变量的组合。

pythonpattern_match.py
def ask(pattern, facts):
    """pattern 形如 ("?c", "ceo", "?p")，? 开头表示变量。"""
    rows = [{}]
    for s, p, o in facts:
        nxt = []
        for b in rows:
            ok, nb = True, dict(b)
            for term, val in zip(pattern, (s, p, o)):
                if term.startswith("?"):
                    if term in nb and nb[term] != val:
                        ok = False
                        break
                    nb[term] = val
                elif term != val:
                    ok = False
                    break
            if ok:
                nxt.append(nb)
        rows = nxt
    return rows

真实端点里，这段逻辑由 SPARQL 引擎完成，但顺序建议不变：先按名称找到实体 URI，再用 URI 写模式，最后加 FILTER 限定范围。千万级三元组的库上，一上来就写宽泛模式，多半会超时或被配额拦住。

三个图谱之间靠 owl:sameAs 一类对齐声明相连，这也是「同一实体多个来源」的合并依据。

0531 个实体能答什么

下面这段程序用内存三元组模拟一个开放图谱子图：9 家公司、若干人物、城市与行业，共 31 个实体、107 条三元组，然后用同一套模式匹配回答三类问题。

实体数      : 31
三元组数    : 107
2 跳邻居（起点：星海科技）
  第 1 跳   : 3 个实体
    - 陈明    （创始人→/CEO→）
    - 杭州    （总部→）
    - 云计算   （行业→）
  第 2 跳   : 2 个实体
    - 云图数据  （←行业）
    - 数聚信息  （←行业）
查询 1      : 星海科技的 CEO 是谁 -> 陈明（1 条）
查询 2      : 云计算行业有哪些公司 -> 星海科技、云图数据、数聚信息（3 条）
缺失示例    : 星海科技 -上游供应商-> ?  -> 0 条
缺失原因    : 开放图谱只收录公司、人物、城市、行业等公共骨架，
              供应商、产能、毛利率等行业深度关系不在其中。
结论        : 开放图谱解决冷启动（31 个实体即可回答 CEO/行业问题），
              不解决行业深度（供应链查询 0 条，需行业图谱补充）。

把最后两行读成一句话：开放图谱解决冷启动，不解决行业深度。31 个实体就能回答 CEO 与行业问题，两跳之内还能找到同行的两家公司；但 107 条三元组里没有一条供应商关系，问「上游供应商是谁」只能得到 0 条。

这也解释了为什么行业项目通常两步走：先用开放图谱把实体和基础关系补齐，再用内部数据补上供应链、产能、合同这些真正支撑判断的关系。

06补一条供应链

任务：在示例数据里给云图数据补一条「上游供应商—恒芯半导体」，再跑一次两跳邻居，记录星海科技的第 2 跳实体从 2 个变成几个。

判断：把下面四个问题分成「开放图谱能答」与「必须行业图谱」两类：星海科技总部在哪、星海科技属于哪个行业、星海科技的最大供应商是谁、星海科技去年毛利率多少。分完请用一句话说明分界依据。

验收：能指出缺失的两类关系都是「只在企业内部或交易记录里出现」的知识。下一步见 知识图谱在行业分析中的三类作用。
