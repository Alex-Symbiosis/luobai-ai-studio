结构化输出与任务判定

让模型「写一段发票信息」，它写得通顺但字段时有时无；让它「填一张发票表」，字段缺失会被校验直接拦下。结构化输出要的不是好文笔，而是程序能直接消费的数据。

认知路线 真实问题→ 直觉类比→ 形式化定义→ 结构与机制→ 案例→ 练习

学习目标

  1. 能区分自由文本输出与结构化输出。
  2. 能为一个需求写出包含字段、类型、必填项的 schema。
  3. 能用「任务—输出—指标」三列完成需求判定。

01让模型填表，为什么总缺字段

财务要自动录入发票。模型返回一段话：「发票金额 1200 元，开票日期 3 月 5 日，销售方为某某公司。」人读得懂，程序没法直接入库。

缺的到底是模型能力，还是输出格式？

是格式。自由文本没有字段边界，程序只能再写一套解析规则，而解析规则本身又会出错。要解决的是「输出必须符合 schema」。

02填表 vs 写作文

写作文可以自由发挥，填表必须每格都有内容，且类型要对：日期不能填成「大概三月」，金额不能填成「一千多」。

直觉结论

结构化输出 = 约定的字段集合 + 明确的类型 + 可执行的校验。三者缺一，输出就退回成「一段话」。

03schema 约束的四个要素

要素作用示例
字段名程序按名取值invoice_no、amount、issue_date
类型保证可计算string、number、date
必填缺了就报错，不静默通过required: [invoice_no, amount]
校验值域与格式约束amount > 0；date 符合 ISO 8601
定义

结构化输出是要求模型产出符合预定义 schema 的对象，而非自由文本的任务。评价不看句子是否通顺，而看字段级准确率与校验通过率。

04三个环节都要卡住

生成时约束把 schema 作为输出格式要求传给模型，减少自由发挥的空间。
返回后校验按类型、必填、值域逐项检查；不通过就重试或转人工，不能默认填默认值。
缺字段要显式原文没有的字段填 null 并标记来源，不能编一个看起来合理的值。

第三点最容易被忽略：模型「补全」一个不存在的发票号，比返回 null 危险得多，因为下游无法分辨真假。

05发票字段抽取

jsoninvoice.schema.json
{
  "type": "object",
  "required": ["invoice_no", "amount", "issue_date"],
  "properties": {
    "invoice_no": {"type": "string", "pattern": "^[0-9]{8,20}$"},
    "amount":     {"type": "number", "minimum": 0},
    "issue_date": {"type": "string", "format": "date"},
    "seller":     {"type": ["string", "null"]}
  }
}
输出校验结果处理
amount: 1200, date: 2026-03-05通过直接入库
amount: "一千二"类型错误重试一次，仍失败转人工
缺 invoice_no必填缺失退回，不允许补默认值
seller: null通过入库并标记「原文未提供」

06六个需求的任务判定表

任务：为六个需求完成「任务类型 + 输出 schema + 评价指标」三列表。

需求任务类型输出（schema 要点）指标
发票录入结构化输出单号/金额/日期，必填 3 项字段级准确率
客服录音转写转录纯文本 + 时间戳CER

验收：schema 的每个字段都能被程序校验；指标能落到「字段级」或「样本级」的具体口径，而不是笼统的「准确率」。
