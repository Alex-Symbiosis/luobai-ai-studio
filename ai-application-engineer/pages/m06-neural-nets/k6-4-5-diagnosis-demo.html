训练诊断：loss 不降先查什么

loss 不降时，最贵的错误是先加容量。先分清是欠拟合、过拟合，还是数据本身有问题。

认知路线 真实问题→ 直觉类比→ 形式化定义→ 结构与机制→ 案例→ 练习

学习目标

  1. 能按「数据与标签 → 初始化与学习率 → 容量」的顺序排查训练异常。
  2. 能读懂同一网络在两种初始化下的训练/验证损失差异。
  3. 能根据两条曲线的四种形态，给出对应的下一步动作。

01例会上的第一反应

周会，有人报：模型训了 40 轮，训练损失 0.66，验证损失 0.97，两条线几乎是平的。会议室里第一个提议是「加两层、加到 256 宽」。

这个提议可能对，但不该是第一步。两条线都高且接近，说明模型在训练集上都没学明白，加容量只是其中一种可能；更常见的原因是学习率不对、初始化不对，或者标签本身有问题。

同样一句「loss 不降」，至少有三种不同的病因。

分辨它们不需要更多算力，只需要两个对照：换一次初始化、把学习率调一个量级。下面这个 Demo 就是第一个对照。

02先分叉，再开药

诊断像分诊：先判断病人属于哪一类，再决定挂哪个科。曲线的形状就是那张分诊单——两条线一起高、只差一条、还是反着来，指向完全不同的处理。

直觉结论

加容量只能治「训练集都学不会」。如果训练集已经 0.99 而验证 0.72，加容量只会让分叉更大。

03三步排查顺序

先数据，再优化，最后才是容量。顺序不能反，因为后一步的前提是前一步已经排除。

步骤查什么怎么查典型发现
① 数据与标签标签对齐、缺失、泄漏抽 20 条人眼看；打乱标签应显著变差标签错位、验证集混进训练
② 初始化与学习率是否全零、步长是否合适换 he_normal；学习率上下各试一个量级全零退化、步长过大发散
③ 容量与正则宽度、深度、正则强度先在小样本上过拟合，再加正则容量不足或正则过强

还有一个快速判别法：取 20 条样本，关掉所有正则，训练到损失接近 0。做不到，说明是优化或实现问题，不是容量问题；做得到而全量数据做不到，才轮到容量与正则。

学习率的排查也可以很便宜：把 0.1 分别换成 0.01 与 1.0，各跑五轮。损失变平说明步长偏小，稳定下降说明接近合适，出现 nan 说明步长过大。三个结果对应三种判断，比一次网格搜索省得多。

两种曲线别读反

训练高、验证低不是「模型很好」，通常意味着数据泄漏、验证集太简单，或者 Dropout / BN 的模式没切对。

04只换初始化

Demo 的设计尽量少变量：同一份数据、同一个种子、同一个优化器与轮数，只有 kernel_initializer 不同。

pythond6_4_init.py
import os
os.environ["TF_CPP_MIN_LOG_LEVEL"] = "3"
import numpy as np
import tensorflow as tf

tf.keras.utils.set_random_seed(0)
rng = np.random.default_rng(0)
n = 400
r = np.concatenate([rng.uniform(0.0, 0.6, n // 2),
                    rng.uniform(0.8, 1.2, n // 2)])
t = rng.uniform(0, 2 * np.pi, n)
X = np.c_[r * np.cos(t), r * np.sin(t)].astype("float32")
y = (r < 0.7).astype("float32")

def build(init):
    return tf.keras.Sequential([
        tf.keras.layers.Input((2,)),
        tf.keras.layers.Dense(16, activation="tanh",
                              kernel_initializer=init),
        tf.keras.layers.Dense(1, activation="sigmoid",
                              kernel_initializer=init),
    ])

数据是一个圆环：内圈半径 0–0.6 记 0 类，外圈 0.8–1.2 记 1 类，中间留一道空带。这个任务需要网络画出一个圆，单层做不到，16 个 tanh 单元够用——前提是这 16 个单元真的各不相同。

每次训练前都重置一次种子，是为了让两组实验的初始随机性一致，差异只来自初始化方式本身。

05实测读数

text实测输出 · TF 2.21.0 / Python 3.13.14
全零     首层不同权重向量  1 个  |w| 均值 0.0000  训练损失 0.6618  验证损失 0.9775
He 正态  首层不同权重向量 16 个  |w| 均值 0.8165  训练损失 0.3616  验证损失 0.5705
全零网络对首样本输出: [0.4991999864578247]
读数 1

1 个 vs 16 个

全零那行只数出 1 个不同的权重向量，16 个隐藏单元被压缩成 1 个；这是损失的根因。

读数 2

0.6618 / 0.9775

训练都比验证低不了多少，但两者都高——不是过拟合，是容量被初始化废掉了。

读数 3

0.3616 / 0.5705

同样轮数，He 初始化把训练损失压到一半，验证损失也明显下降，差距立现。

正确的结论：全零那份不是「梯度为零所以完全不学」。梯度不为零，参数一直在动，全零网络对首样本输出 0.4992 也不是 0.5 以外的随机值——只是 16 个单元始终同步，等效宽度为 1，学不出圆环的边界。

这也说明为什么诊断顺序里「初始化」排在「加容量」之前：这次加宽到 256，仍然是 1 个有效单元，只会更慢，不会更好。

06给你三条曲线

任务：下面三种情况，各写出「最可能的原因」与「下一步先做什么」，不要直接写「加容量」。

情况训练损失验证损失
A0.69 不降0.69 不降
B0.020.65 且回升
C0.150.12

追问：① A 情况里，若把标签整体打乱后损失几乎不变，说明什么？② B 情况该先加 Dropout 还是先加数据？③ C 情况还需要做什么？

验收：三问都按「先数据、再优化、后容量」的顺序回答，并能引用本页的两行读数说明「初始化能让有效宽度从 16 掉到 1」。相关背景见 初始化 与 批归一化。

注：本页需 NumPy 辅助计算，运行口径为 tensorflow-cpu 2.21.0 + Keras 3.15.1 + NumPy 2.5.5 + Python 3.13.14（Windows 原生 CPU），输出为本机实测，可直接复现。
