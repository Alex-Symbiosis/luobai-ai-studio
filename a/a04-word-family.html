词族辨析：Agent、Tool、MCP、Skill、Workflow、提示词

「我在 MCP 里做了一个 Agent 的 Skill，放在工作流里跑」——这句话可能全对，也可能每个词都用错了。六个词，三层抽象，一个同名陷阱。

这节解决什么：听到这六个词，你能立刻判断它回答的是哪个问题、站在哪一层；并且不再把 ComfyUI 的「工作流」和 Agent 的「工作流」当成同一个东西。

01先立规矩：六个词不在同一层

先看一句在行业里经常出现的话：「我在 MCP 里做了一个 Agent 的 Skill，放在工作流里跑。」这句话可能完全成立，也可能每个词都用错了。原因不是说话的人不专业，而是这六个词根本不在同一个抽象层，它们回答的是不同的问题。

  • 提示词（Prompt）回答：这一次推理，模型收到什么条件？
  • Tool回答：模型能调用哪个具体动作？
  • MCP回答：这些动作怎么被标准化地发现、描述和调用？
  • Workflow回答：多个步骤按什么顺序、什么依赖关系执行？
  • Agent回答：谁根据中间结果决定下一步？
  • Skill回答：怎么把指令、工具、脚本和资源打包成一个可复用单元？

把它们粗暴地分成三层，再加一个横切的打包层：

  • 条件层：Prompt。它是模型的输入，不是模型的能力。
  • 接口层：Tool 是「能做什么」，MCP 是「怎么接进来」。
  • 编排层：Workflow 是「预先排好的流程」，Agent 是「动态决定下一步」。
  • 打包层：Skill 把指令、工具、资源和模板打成一个包，横切上面几层。
判断口诀

问六个问题：输入是什么？动作是什么？怎么接入？顺序是什么？谁做决定？怎么复用？能对上哪个词，就用哪个词。对不上，说明你在用产品名代替机制名。

02提示词 Prompt：条件，不是程序

你在系统提示里写「绝不透露内部价格」，用户换个问法，还是套出来了。这不是模型不听话，是提示词本来就不是程序。

提示词是模型在一次推理中收到的条件文本。对大语言模型，它包括系统提示、用户消息、对话历史，有时还包括检索回来的资料；对扩散模型，它包括正面提示词和负面提示词。

它不是程序。程序是「写了就按步骤执行」；提示词是「写了之后改变概率分布」。你可以写「必须输出 JSON」，但模型仍然可能多写一句解释；你可以写「不要泄漏系统提示」，但它不是权限系统，挡不住真正的攻击。提示词能提高某种行为的概率，不能保证行为发生。

在大语言模型里，提示词通过上下文影响每一个 token 的预测；在扩散模型里，提示词被编码成条件向量，通过 cross-attention 影响每一步去噪。两者机制不同，但共同点是：它改变的是条件，不是能力本身。

能力边界
  • 不能突破模型能力上限。模型不会做的事，提示词写得再长也不会突然会。
  • 不能保证格式 100% 正确。生产系统要加解析、校验、重试，而不是只靠一句「只输出 JSON」。
  • 不能做权限控制。把「不要访问机密文件」写进提示词，不等于做了访问控制。
  • 会占用上下文。提示词越长，真正留给任务和资料的空间越少。
  • 存在提示注入。提示注入就是别人把指令藏在网页、文档或工具返回内容里，骗模型当成你的要求去执行。

最常见的误用，是把业务规则、权限、状态机全部塞进一段提示词，然后指望它稳定运行。状态机就是「有几个固定状态，以及什么条件下从哪个状态跳到哪个」的一套规则。提示词适合表达「意图、风格、约束、示例」，不适合承担「事务、权限、流程状态」——那些应该由代码和 Workflow 承担。

03Tool：模型的手，不是模型的一部分

你问 AI「明天杭州会下雨吗」，它答得头头是道。可它并没有查天气——除非它手上有 get_weather 这个工具，而且宿主程序真的替它执行了。

Tool（工具 / 函数调用）是一个带名字、描述、参数结构和返回值的可调用函数，被暴露给模型。比如 get_weather(city)、search_web(query)、create_ticket(title, priority)。

关键机制是分工：

  1. 模型根据任务和工具描述，输出一个结构化的调用意图：工具名 + 参数，通常写成 JSON（一种结构化的键值文本格式）。
  2. 宿主应用的运行时（runtime）校验参数、检查权限、真正执行函数。
  3. 执行结果作为一条消息回填给模型。
  4. 模型基于结果继续生成，或者发起下一次调用。

模型自己不执行。它只是决定「调什么、传什么」。没有 runtime，工具描述只是一段文本；没有权限系统，工具就是一个没有门锁的接口。

沿用本课标题这个比喻：Tool 是模型的手。模型自己不伸手，它只决定“伸哪只手、往哪伸”；真正把动作做出去的是宿主程序的 runtime。手再灵活，也得有人允许它伸进那个区域。

能力边界
  • 参数可能编造。模型会给出不存在的城市、错误的日期、类型不对的字段，runtime 必须校验。
  • 工具可能选错。工具越多、描述越模糊，选择错误率越高。
  • 返回值不可信。工具返回的网页内容、用户输入、第三方数据都可能包含提示注入。
  • 副作用要自己管。发邮件、下单、删文件不是「查询」，需要幂等、确认、审计和回滚。
  • 单次调用不是 Agent。没有循环、没有根据结果改变下一步，就只是一次函数调用。

04MCP：工具接入的插座标准

同一个工具，在三个 AI 应用里要写三套接入代码——这是过去几年最常见的浪费。MCP 要解决的就是这件事。

MCP（Model Context Protocol）是一套开放协议，用来让模型应用以标准方式发现和调用外部能力。它基于 JSON-RPC 2.0（一种用 JSON 传请求和响应的通信格式），采用 client–server 结构：宿主应用里跑 MCP client，工具提供方跑 MCP server，双方交换能力描述、调用请求和结果。

它主要标准化三类东西：

  • Tools：可调用的函数，带名称、描述、参数结构。
  • Resources：可读取的数据或文件，供应用加载到上下文。
  • Prompts：可复用的提示模板，供用户或应用选择。

它解决的是「集成碎片化」：以前每接一个工具，都要为某个应用写一套私有适配；有了统一协议，工具提供方写一次 server，多个支持 MCP 的应用都能发现并调用。

沿用本课标题这个比喻：MCP 是插座标准。它规定插座形状、供电和数据怎么传，让设备即插即用。但它不生产外设，不决定你该插什么，也不保证插上的设备安全可靠。

能力边界
  • MCP 不提供智能。它不会规划、不会推理，只负责「怎么描述和调用」。
  • MCP 不是 Agent。接了 MCP 不等于有了自主决策循环。
  • server 是信任边界。恶意 server 可以返回提示注入内容，诱导模型泄露数据或执行危险操作。
  • 工具描述会占上下文。接得越多，模型选择越困难，成本也越高。
  • 协议统一不等于质量统一。一个 MCP server 是否可靠、是否有权限控制、是否幂等，仍要逐个评估。

常见误用是把 MCP 当成「模型能力」或「Agent 框架」。更准确的表述是：MCP 是工具接入层的基础设施，和「模型有多聪明」「Agent 会不会规划」是两件不同的事。

05Workflow：一个词，两张图

同事说「把这个做成工作流」。你要先问一句：他说的是「谁先谁后」，还是「谁喂谁」？答错这一句，后面会白做半天。

Workflow 的通用含义是：把多个步骤按依赖关系组织成一个可重复执行的流程，通常是一个有向无环图（DAG）——箭头有方向，而且顺着箭头走不会绕回起点。但它在两个语境里指的东西很不一样。

含义 A：Agent / 业务编排语境

节点是「调用模型」「调用工具」「人工审核」「条件分支」，边是控制流——上一步完成后走下一步，满足条件走哪个分支。步骤由人预先设计好，模型只在某些节点内部做判断。Dify、Coze、n8n 里的工作流，客服工单流转，内容审核流水线，都属于这一类。

它的优势是可控、可测、成本可预估；局限是只能走设计好的路径，遇到没预料的情况不会自己改流程。

含义 B：ComfyUI 语境

节点是「加载模型」「编码提示词」「采样」「解码」「保存图像」，边是数据流——张量、图像、条件向量从上一个节点流向下一个节点。执行引擎按依赖关系做拓扑排序，缓存没有变化的中间结果。它是一张计算图，不是业务流程。

它的优势是透明、可复现、可精细控制每一步；局限是它不会自己决定「要不要再来一次」，也不会根据结果改变图结构——图是你连的，顺序是依赖决定的。

对比项Workflow 含义 A：业务 / Agent 编排Workflow 含义 B：ComfyUI 节点图
节点是什么业务动作：调用模型、调用工具、人工审核计算算子：加载、编码、采样、解码
边上传什么控制信号、状态、少量数据张量、图像、条件向量
谁决定顺序人设计的分支与条件依赖关系与拓扑排序
能否自己改流程不能，除非设计时留了分支不能，图结构是静态的
典型失败步骤卡住、审批超时、分支漏判接线错误、维度不匹配、显存不足
如何复现流程版本 + 输入 + 运行日志工作流 JSON + 模型文件 + 种子 + 自定义节点版本

为什么容易混？英文是同一个词；两者都画成「框和箭头」；中文都翻译成「工作流」。但只要问一句就分开了：箭头代表的是「先做这个，再做那个」，还是「把这个数据喂给那个节点」？

一句话记法：Agent 的工作流决定「谁先谁后」，ComfyUI 的工作流决定「谁喂谁」。两者都是 DAG，都追求可复现，都可以保存、分享、版本化——这是它们真正的共同点。

先记一句：图里那排小框是 ComfyUI 的节点名——Checkpoint（整套模型文件）、CLIP（文本编码）、KSampler（采样器）、VAE（解码器）、潜变量（压缩后的草稿）。它们分别在 L0-01 与 D 层 L1 系列里讲透。这里只看箭头传什么。

06Agent：带循环的决策系统

你让它「查一下竞品价格，做成表格」。它搜了一次，发现数据不全，自己换了关键词再搜，最后才输出。这个「自己决定再来一次」的动作，就是 Agent 和普通调用的分界。

Agent 不是「更高级的聊天机器人」，而是一个带循环的决策系统。它至少包含五件事：

  • 模型：负责理解任务、选择动作、生成参数。
  • 工具：动作空间。没有工具，它只能说话。
  • 状态 / 记忆：记录已经做了什么、看到了什么，避免原地打转。
  • 循环：观察 → 规划 / 选择动作 → 调用工具 → 观察结果 → 更新状态 → 继续。
  • 终止条件：任务完成、达到最大步数、预算耗尽、需要人工确认。

判据只有一条：它能不能根据中间结果改变下一步？能，就是 Agent；不能，就是固定 Workflow。一个只会回答问题的聊天机器人，没有工具、没有循环，不叫 Agent；一个按固定顺序调用五个工具的系统，没有根据结果改变路径，也不叫 Agent。

比喻：Workflow 是整条产线，工序写死；Agent 是拿到图纸后自己决定下一道工序的工头。但工头也需要岗位手册（Skill）、一只手（Tool）和这条产线（Workflow）——它们不是互斥关系。

能力边界
  • 错误会累积。第一步搜错，后面会基于错误信息继续推理。
  • 成本和时延不可预测。它可能调用 2 次工具，也可能调用 20 次。
  • 需要护栏：最大步数、预算上限、沙箱（受限的运行环境，碰不到系统其他部分）、权限、危险操作人工确认。
  • 评估困难。同一个任务，不同 Agent 走不同路径，不能只看最终答案。
  • 工具越多，选择越难。动作空间变大，规划错误率上升。

常见形态包括「单 Agent + 多工具」「带长期记忆的 Agent」「多 Agent 分工」。多 Agent 听起来高级，但它首先放大了协调成本、通信成本和错误传播；在任务边界清晰、步骤固定的场景里，Workflow 往往更便宜、更可靠。

07Skill：把「怎么做」打包

同一套「写周报」的流程，你在每个对话里都要重新交代一遍。Skill 就是把这份交代、附带的模板和脚本收进一个文件夹，下次直接调用。

Skill 是六个词里定义最不统一的一个，必须看你所用的平台。主流有两种含义：

含义 A：能力包 / 指令包

以 Anthropic 的 Agent Skills 为代表：一个文件夹，里面有 SKILL.md（说明何时使用、具体怎么做）、参考文档、模板、可选的脚本和资源。模型先看到简短的名称和描述，判断相关后再加载正文，需要时再读取资源——这叫渐进披露：先用一句摘要让人判断要不要看，需要时再展开正文。它主要改变的是「模型怎么做」，不是「模型能做什么」。

含义 B：平台里的预置能力

有些产品把「封装好的工具」叫 Skill，有些把「工作流模板」叫 Skill，还有的把「一组提示词 + 知识库」叫 Skill。名字一样，实质可能是 Tool，也可能是 Workflow。

判断方法还是回到机制：它是在给模型加说明书（Skill 含义 A），还是在给模型加一只手（Tool），还是在排好步骤（Workflow）？三者可以同时出现在一个 Skill 包里，但不要因此把概念混掉。

比喻：Skill 是「岗位手册 + 工具箱 + 模板文件」打包成的工种包。手册告诉模型怎么做事，工具让它能做事，模板减少重复劳动。

能力边界
  • 不能突破模型能力。说明书再详细，模型不会的能力还是不会。
  • 文档越长越占上下文。按需加载正是为了避免一次塞满。
  • 脚本执行仍需权限与沙箱。Skill 里有代码，不等于可以无条件运行。
  • 格式不通用。不同平台的 Skill 目录结构、元数据、加载方式可能不同。
  • 版本与依赖要管理。脚本依赖、模板版本、工具接口变化都会让 Skill 失效。

08谁包含谁：关系图与速查表

先给结论：这六个词不构成一棵干净的包含树。它们之间是「包含」「调用」「服务」「打包」几种不同关系，混在一起问「谁包含谁」，一定会得到错误答案。

  • Agent 包含模型、工具、状态 / 记忆、循环与终止条件。
  • Workflow 与 Agent 可以互相嵌套：一个 Workflow 可以把「调用 Agent」作为其中一个节点；一个 Agent 也可以把「执行某个固定 Workflow」作为一步。谁在上层，取决于谁决定流程。
  • MCP 服务于 Tool：它不包含工具的业务语义，只规定工具怎么被发现和调用。
  • Prompt 在模型入口：Agent、Workflow、Skill 都可能生成提示词，但提示词本身不是编排。
  • Skill 是打包方式：它可以包含指令、工具、脚本、资源，横切各层，不参与「谁包含谁」的主干关系。
词一句话所在层谁调用它典型载体最常见误用
Prompt这一次推理的条件文本条件层模型消费；其他层生成系统提示、用户消息、负面提示当成程序或权限控制

Agent带循环的自主决策系统编排层用户或系统触发编码 Agent、客服 Agent有工具就叫 Agent

把六个词串成一句话：提示词是这一班的任务单，Tool 是手，MCP 是插座，Workflow 是流水线，Agent 是会自己决定下一道工序的工头，Skill 是岗位手册加工具箱。比喻只帮你定位，真正判断还是要回到机制。

09常见误解

  1. 「模型用了工具，就是 Agent。」

    单次函数调用没有循环，也没有根据结果改变下一步。它只是「模型 + 工具」，不是「模型 + 工具 + 循环 + 状态 + 终止条件」。Agent 的核心是决策循环，不是工具数量。

  2. 「MCP 是一个模型，或者一种 Agent 框架。」

    MCP 是接口协议，规定工具怎么被发现、描述和调用。它不含模型权重，也不含规划逻辑。接上 MCP，模型还是那个模型，Agent 还是要自己写循环。

  3. 「Workflow 和 Agent 是对立的，只能二选一。」

    生产系统里常见「Workflow 骨架 + Agent 节点」：大部分步骤固定，只有需要开放判断的那一步交给 Agent。它们可以互相嵌套，取决于谁决定流程。

  4. 「Skill 就是一段提示词。」

    Skill 可能包含提示词，但通常还包含参考文档、模板、脚本和资源。把 Skill 等同提示词，会忽略它的加载机制、权限边界和依赖管理。

  5. 「ComfyUI 的工作流就是 Agent 的工作流。」

    同名不同物。ComfyUI 是计算图，边传张量与条件，顺序由依赖拓扑决定；Agent 工作流是控制流，边传控制与状态，顺序由人设计的分支决定。判断看节点和边，不看名字。

  6. 「提示词写得好，就等于模型能力变强了。」

    提示词是把模型已有能力「引导出来」，不是「创造出来」。它能提高命中率，不能突破能力上限。评估一个系统时，要区分「提示词工程」和「模型/工具/流程」的贡献。

  7. 「Agent 一定比 Workflow 高级、更好。」

    固定任务里，Workflow 更便宜、更可控、更容易测试和审计；Agent 适合步骤不确定、需要根据中间结果调整的开放任务。选型看任务，不看名词的新旧。

  8. 「MCP server 接得越多，系统就越强。」

    工具描述会占用上下文，工具越多选择越难，攻击面也越大。应该按任务最小化工具集，逐个评估权限、幂等性和返回内容的可信度。

  9. 「模型调用工具，就是模型在执行代码。」

    模型只输出调用意图和参数，真正的执行发生在宿主应用的 runtime 里。权限校验、沙箱、审计都应该在 runtime 做，而不是指望模型自觉。

10自检清单与场景判断

先勾选，再做下面的六个场景题。能说清「为什么」，比选对词更重要。

六个场景，判断它是什么

  1. 你在 Dify 里拖了五个节点：接收问题 → 搜索资料 → 总结 → 生成报告 → 发送邮件。顺序固定，没有分支。

    查看答案

    Workflow（含义 A，控制流）。步骤由人预先设计，模型只在节点内执行任务，没有根据中间结果改变路径。它不是 Agent。

  2. 同一个系统改成：模型看完搜索结果后，自己决定要不要换关键词再搜，最多五轮；够了才生成报告。

    查看答案

    Agent。它具备循环、状态和终止条件，并根据中间结果改变下一步。外层的「最多五轮」是护栏，不改变它是 Agent 的事实。

  3. 你给模型一个 get_weather(city) 的函数描述，模型输出 {"city":"天津"}，你的后端收到后去请求天气 API，再把结果回填。

    查看答案

    Tool（函数调用）。模型只发起调用意图，后端 runtime 真正执行。没有循环，所以不是 Agent。

  4. 你把公司内部数据库封装成一个 MCP server，Claude Desktop 启动后能列出可用工具并调用查询。

    查看答案

    MCP（接口协议）+ Tool（具体查询能力）。MCP 负责发现、描述和调用；它本身不提供智能，也不是 Agent。

  5. 你写了一个文件夹：SKILL.md 说明何时使用、附了报告模板和两个处理脚本，模型按需读取。

    查看答案

    Skill（含义 A，能力包 / 指令包）。它把指令、模板、脚本和资源打包，按需加载；不是单纯的提示词，也不是一个工具函数。

  6. 你在 ComfyUI 里把「加载 Checkpoint → CLIP 文本编码 → KSampler 采样 → VAE 解码 → 保存图像」连成一张图。

    查看答案

    Workflow（含义 B，数据流 / 计算图）。边传的是模型、条件、潜变量和像素；执行顺序由依赖拓扑决定。它不是 Agent 工作流，ComfyUI 本身也没有自主决策循环。

进入 ComfyUI 前，把四个词对号入座

你会在 ComfyUI 里反复遇到下面这些词。用本课的框架定位，就不会被名字带跑：

  • workflow（节点图）：含义 B，计算图 / 数据流图。它既决定「谁喂谁」，也决定「谁先谁后」——数据依赖本身就是先后关系。
  • prompt（正面 / 负面提示词）：条件层。它连接文本编码器，产出条件向量，不是聊天框。
  • custom node（自定义节点）：算子插件，扩展 ComfyUI 能做的计算。它不是 Tool，也不是 MCP；只有当你让它发起外部 API 调用时，才接近 Tool 的角色。
  • API 节点：真正的外部调用，可以类比 Tool；如果通过标准协议接入，才谈得上 MCP。
  • checkpoint / LoRA / ControlNet：模型权重与条件模块，是「模型层」的零件，不是 Agent，也不是 Skill。

ComfyUI 没有自主决策循环。除非你在外面套一个 Agent，通过 API 去调用它、根据出图结果决定下一步，否则它始终是一张由你连好的计算图。
